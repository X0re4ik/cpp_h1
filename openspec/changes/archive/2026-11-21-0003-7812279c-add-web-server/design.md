# Design

## Context

См. `proposal.md` — Why. Текущее состояние, важное для реализации:

- В рабочей копии уже есть незакоммиченный черновик `h1::io_server` на
  Boost.Asio: `RequestParser`, `APIRouter`, `Connection`,
  `ConnectionManager`, `IOServer`, `TaskManagerHandler`, `cmd/server_main.cpp`,
  `src/test_request_parser.cpp`, `loadtest.py`.
- `TaskManagerHandler` вызывает расчёт, но возвращает `request.body` вместо
  результата; JSON-ответа и обработки ошибок нет.
- `DBManager` в черновике защищён `std::mutex`, но в
  `registerNewOperation()` стоит два `lock_guard` на одном мьютексе — вставка
  в БД самоблокируется. `CalcLocalCache` также защищён мьютексом.
- Модули `jsonp`, `calc`, `calculation::CalculationService`, `db`, `lcache`
  переиспользуются сервером как есть; их интерфейсы менять не требуется, кроме
  аккуратной потокобезопасности.
- Ограничение ДЗ-3 «без многопоточности» для серверного режима снято явным
  решением владельца (см. proposal.md). Для CLI-кода ограничение сохраняется.
- Тесты — GoogleTest; тестовые файлы регистрируются в
  `add_executable(h1_test ...)`.

## Goals / Non-Goals

**Goals:**

- Довести существующий черновик `io_server` до рабочей ручки
  `POST /h1/task` с JSON-контрактом из `specs/http-api/spec.md`.
- Исправить взаимную блокировку при записи в БД и подтвердить, что
  многопоточная обработка не приводит к гонкам.
- Добавить конфигурацию сервера (CLI + env), прогрев кеша и корректную
  инициализацию логгера.
- Включить сервер в deb-пакет и systemd.
- Покрыть unit-тестами роутер, хендлер и конфигурацию сервера.
- Подтвердить прогоном `loadtest.py`, что многопоточный сервер не блокируется
  и не падает под конкурентной нагрузкой.

**Non-Goals:**

- Новые прикладные ручки (health, history, cache management) — только
  `POST /h1/task`.
- Переход на Boost.Beast, cpp-httplib или другой HTTP-стек.
- Keep-alive, chunked transfer encoding, HTTPS/TLS, CORS, аутентификация.
- Изменение формата CLI-вывода, схемы БД, ключей кеша.
- Интеграционные unit-тесты с реальным PostgreSQL: unit-тесты используют
  моки, а работа с реальной БД проверяется отдельным smoke/нагрузочным прогоном
  `loadtest.py`.

## Decisions

1. **Развиваем существующий `io_server`, а не переписываем стек.**
   Boost.Asio уже подключён, парсер и роутер покрыты тестами, черновик
   компилируется в составе `h1_core`. Альтернатива — cpp-httplib/Boost.Beast:
   меньше/больше кода, но требует удаления существующего модуля и новой
   зависимости. Отклонено как избыточное для одной ручки.

2. **Сервис расчёта возвращает структуру, а не пишет в поток.**
   `ISmartCalculatorService::calculate()` меняет сигнатуру с `void` на
   `CalculationReply` (операция, операнды, `result`, `errorMessage`,
   `isSuccess`, `fromCache`). Хендлер сериализует её в JSON. Это отделяет
   вычисление от HTTP-представления и позволяет тестировать контракт без
   сокетов. Ошибки парсинга/вычислений пробрасываются исключениями и
   перехватываются в хендлере.

3. **Ответ формируется через nlohmann/json.**
   В `TaskManagerHandler` строится `nlohmann::json`, сериализуется в строку,
   выставляются `Content-Type: application/json` и `Content-Length`. Для
   факториала ответ содержит `value`, для бинарных операций — `left/right`.
   Любое исключение → HTTP 500 и `{"error": "<текст>"}`. Альтернатива —
   ручная склейка строк: отклонено из-за экранирования и ошибок формата.

4. **Коды ответов: 200/500 для ручки, 404/405 для маршрутизации.**
   Это соответствует решению владельца «только 200 и 500» для `/task`:
   ошибки обработки запроса не маскируются под 4xx, а маршрутизация остаётся
   стандартной. Роутер не меняет свою семантику.

5. **Конфигурация — отдельный модуль `ServerConfig`.**
   Новый `include/h1/io_server/server_config.hpp` + `src/io_server/server_config.cpp`
   инкапсулирует разбор `--host/--port/--threads/--verbose/--help` через уже
   используемый `argparse`, переменные `H1_SERVER_*` через `libenvpp` и
   значения по умолчанию. Приоритет CLI → env → default. `--help` обрабатывается
   до подключения к БД. Альтернатива — разбор в `main`: отклонено, так как
   конфигурацию нужно тестировать.

6. **Прогрев кеша — общая функция.**
   Логика `warmUpCache` из `src/application.cpp` выносится в переиспользуемую
   функцию (например, `h1::warmUpLocalCache(ICalcLocalCache&, IDBManager&)` в
   `include/h1/application.hpp` / `src/application.cpp` либо отдельный
   небольшой модуль). CLI и сервер вызывают её до обработки запросов.
   Альтернатива — дублировать цикл в `server_main.cpp`: отклонено.

7. **Многопоточность остаётся в `IOServer`.**
   `io_context` обслуживается пулом из `countThreads_ + 1` потоков; число
   потоков задаётся конфигурацией. `DBManager` сериализует доступ к `PGconn`
   одним мьютексом (без повторного захвата), `CalcLocalCache` — своим.
   Альтернатива — однопоточный asio: отклонено владельцем, так как нужна
   пропускная способность под нагрузкой. Риск: `PGconn` один на процесс,
   поэтому БД-операции фактически последовательны; это принято.

8. **Упаковка: только серверный режим.**
   Пакет называется `h1-server` и содержит только `h1Server`,
   `packaging/systemd/h1-server.service` (`Type=simple`,
   `Restart=on-failure`, `EnvironmentFile=-/etc/h1/h1-server.env`,
   `ExecStart=/usr/bin/h1Server`) и
   `packaging/etc/h1/h1-server.env` с `DB_*` и `H1_SERVER_*`. CLI-бинарник
   `h1`, юнит `h1.service` и конфиг `/etc/h1/h1.env` в пакет не входят:
   CLI-приложение собирается только для разработки и тестов. Env-файл
   сервера регистрируется как conffile.

9. **Тесты — unit, без реальной БД.**
   `src/test_io_server_router.cpp` — маршрутизация; 
   `src/test_task_manager_handler.cpp` — хендлер с `MockDBManager` и
   `MockCalcLocalCache` (успех, cache hit, ошибка вычисления, невалидный JSON);
   `src/test_server_config.cpp` — приоритеты CLI/env/default и `--help`.
   Все файлы добавляются в `add_executable(h1_test ...)`.

## Risks / Trade-offs

- [Единственный `PGconn` при многопоточности] → доступ сериализуется мьютексом;
  корректность важнее пропускной способности. При необходимости пул соединений
  — отдельный change.
- [Повторный захват мьютекса в `DBManager`] → исправляется в этом change:
  один `lock_guard` на функцию; добавлен unit-тест хендлера, который проходит
  через `registerOk`/`registerError`.
- [Ошибки вычисления маскируются под 500] → это согласованный контракт; текст
  ошибки передаётся в поле `error`, клиент может его показать.
- [Парсер не поддерживает chunked/keep-alive] → вне scope; сервер закрывает
  соединение после ответа, как в черновике.
- [Тесты без реальной БД не поймают ошибки SQL и блокировки] → принято
  владельцем; ручные smoke-кейсы и нагрузочный прогон `loadtest.py` в
  `manual-tests.md` покрывают реальный запуск, проверяют отсутствие
  взаимоблокировок и падений под конкурентной нагрузкой.
- [Сериализация доступа к единственному `PGconn` под нагрузкой] → мьютекс
  удерживается только на время запроса; `loadtest.py` с конкурентностью 100+
  подтверждает, что запросы не зависают и сервер продолжает отвечать.
- [Изменение состава deb-пакета] → пакет переименован в `h1-server` и больше
  не устанавливает CLI-бинарник `h1` и `/etc/h1/h1.env`; единственный conffile —
  `/etc/h1/h1-server.env`. Пользователям CLI нужно собирать `h1` из исходников.
  Обновление с прежнего пакета `h1` требует отдельного шага удаления (см.
  migration plan).

## Migration Plan

1. Исправить `DBManager` и проверить, что CLI-тесты остаются зелёными.
2. Реализовать `CalculationReply`, JSON-ответ хендлера, конфигурацию сервера,
   прогрев кеша и запуск `h1Server`.
3. Добавить unit-тесты и зарегистрировать их в CMake.
4. Добавить install-правила для `h1Server`, systemd-юнит и env-файл сервера;
   убрать из упаковки CLI-бинарник, `h1.service` и `h1.env`; пересобрать
   deb-пакет `h1-server`.
5. Обновить README.
6. Откат: изменения локализованы в `io_server`, `server_main.cpp`,
   `DBManager`, `CMakeLists.txt`, `packaging/` и `README.md`; откат — через
   git-историю этих файлов. Схема БД и формат данных не меняются.
