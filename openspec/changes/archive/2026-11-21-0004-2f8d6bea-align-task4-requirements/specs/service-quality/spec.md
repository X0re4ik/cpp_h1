# Spec Delta

## Purpose

Гарантии готовности серверного режима `h1` к требованиям ДЗ-4: минимальное
число потоков обработки, сетевой тестовый клиент с проверкой результата и
обязательная проверка ThreadSanitizer.

## ADDED Requirements

### Requirement: Минимум два потока обработки
Сервер SHALL запускать не менее двух потоков обработки. Конфигурация SHALL
отклонять значение `--threads` и переменной `H1_SERVER_THREADS` меньше 2 с
понятным сообщением об ошибке. Значение по умолчанию SHALL быть не меньше 2.

#### Scenario: Значение по умолчанию удовлетворяет требованию
- **WHEN** сервер запускается без `--threads` и без `H1_SERVER_THREADS`
- **THEN** он запускает не менее двух потоков обработки

#### Scenario: Один поток отклоняется
- **WHEN** сервер запускается с `--threads 1`
- **THEN** запуск завершается ошибкой с сообщением о минимуме в 2 потока

#### Scenario: Один поток из окружения отклоняется
- **WHEN** задана `H1_SERVER_THREADS=1` и параметр `--threads` не указан
- **THEN** запуск завершается ошибкой с сообщением о минимуме в 2 потока

### Requirement: Сетевой тестовый клиент
Репозиторий SHALL содержать автоматический тест на GoogleTest, который
поднимает реальный `IOServer` на локальном TCP-порту, подключается к нему по
сети, отправляет `POST /h1/task` и проверяет полученный HTTP-статус и тело
JSON, включая значение поля `result` или `error`. Тест SHALL NOT использовать
`sleep_for` и другие виды сна для ожидания готовности сервера; ожидание SHALL
выполняться busy-циклом с ограничением по времени.

#### Scenario: Успешный расчёт проверяется по телу ответа
- **WHEN** тестовый клиент отправляет `{"left": 2, "right": 3, "operation": "+"}`
- **THEN** тест получает HTTP 200 и JSON, в котором `result` равен 5

#### Scenario: Ошибка вычисления проверяется по телу ответа
- **WHEN** тестовый клиент отправляет `{"left": 10, "right": 0, "operation": "/"}`
- **THEN** тест получает HTTP 500 и JSON с непустым полем `error`

#### Scenario: Невалидный JSON проверяется по телу ответа
- **WHEN** тестовый клиент отправляет тело `not-json`
- **THEN** тест получает HTTP 500 и JSON с непустым полем `error`

#### Scenario: Сервер не поднялся за отведённое время
- **WHEN** тестовый сервер не начал принимать соединения до истечения дедлайна
- **THEN** тест завершается с ошибкой и диагностическим сообщением, не зависая

### Requirement: Проверка ThreadSanitizer
Сборка SHALL предоставлять опцию `H1_USE_TSAN` и цель `tsan-tests`, которые
компилируют и линкуют сервер и тесты с `-fsanitize=thread`. Итоговая версия
сервиса SHALL успешно проходить эту проверку без сообщений о гонках данных и
взаимоблокировках.

#### Scenario: Сборка с ThreadSanitizer
- **WHEN** проект конфигурируется с `-DH1_USE_TSAN=ON` и собирается
- **THEN** сборка завершается успешно, а бинарники содержат TSAN-инструментацию

#### Scenario: Тесты под ThreadSanitizer
- **WHEN** выполняется `ctest` или `tsan-tests` в TSAN-сборке
- **THEN** тесты завершаются успешно без отчётов о data race или deadlock

### Requirement: Документация изменений ведётся в OpenSpec
Проект SHALL оформлять планы и требования изменений в артефактах OpenSpec
(`proposal`, `specs`, `design`, `tasks`). Требование ДЗ-4 о четырёх отдельных
документах с планами SHALL NOT применяться: выбор способа разработки и формата
планов остаётся за разработчиком.

#### Scenario: Изменение описано артефактами OpenSpec
- **WHEN** в проекте создаётся новое изменение
- **THEN** оно содержит proposal, specs, design и tasks в каталоге
  `openspec/changes/<change-name>/`

#### Scenario: Отдельные документы не требуются
- **WHEN** проверяется комплект документации change
- **THEN** наличие файлов `docs/task4-plan-*.md` не требуется, а планы
  берутся из OpenSpec-артефактов
