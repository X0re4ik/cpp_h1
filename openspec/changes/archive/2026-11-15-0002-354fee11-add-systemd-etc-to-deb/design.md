# Design

## Context

См. proposal.md — Why. Текущее состояние: изменения уже внесены в репозиторий
и проверены на реальной установке (расчёт через `systemctl start h1`
работает). Задача change — формализовать уже существующее поведение дельтой
к capability `deb-packaging` и зафиксировать проверку/сверку артефактов,
а не проектировать с нуля.

Состав текущей реализации (факты репозитория):

- `CMakeLists.txt`: install-правила для юнитов (glob по `packaging/systemd/`),
  install конфига в `/etc/h1`, `CPACK_DEBIAN_PACKAGE_CONTROL_EXTRA`
  (postinst, postrm, conffiles);
- `packaging/systemd/h1.service` — юнит `Type=oneshot`;
- `packaging/etc/h1/h1.env` — содержимое конфига (совпадает с `.env.example`);
- `packaging/deb/postinst` — `systemctl daemon-reload` + `systemctl enable h1`
  (автозагрузка юнита при установке, решение подтверждено в apply-фазе);
- `packaging/deb/prerm` — `systemctl disable h1` при удалении пакета
  (добавляется в рамках change, чтобы не оставлять висячие ссылки
  автозагрузки);
- `packaging/deb/postrm` — `systemctl daemon-reload`;
- `packaging/deb/conffiles` — список `/etc/h1/h1.env`;
- `README.md` — раздел «systemd-юниты в пакете».

## Goals / Non-Goals

**Goals:**

- Синхронизировать главный spec `deb-packaging` с фактическим составом
  пакета через дельту (MODIFIED «Состав пакета» + ADDED требования).
- Зафиксировать наблюдаемые гарантии: состав пакета, conffile-семантику,
  `daemon-reload`, поведение юнита и его жизненный цикл (enable при
  установке, disable при удалении).
- Составить ручные smoke-кейсы проверки пакетной функциональности
  (`manual-tests.md`).

**Non-Goals:**

- Изменения C++-кода (модули `include/h1/<module>`, `src/<module>`,
  списки `H1_CORE_SOURCES`, тесты) не затрагиваются.
- Юнит-шаблон `h1@.service`, таймеры по расписанию — возможное будущее
  изменение, в этот change не входит (решение подтверждено владельцем).
- Обработка непойманного исключения в `cmd/main.cpp` при отсутствии
  env-переменных (coredump) — вне scope, кандидат в отдельный change
  (решение подтверждено владельцем).
- Автоматический бэкап env-файла перед обновлением (preinst) — конфликт
  conffile решает dpkg (решение подтверждено владельцем).
- Архитектура приложения (см. openspec/context/architecture.md) не меняется.

## Decisions

1. **Дельта в существующую capability `deb-packaging`, а не новая capability.**
   Юниты и `/etc`-конфиг — это состав и поведение того же deb-пакета;
   заводить отдельную capability для половины одного артефакта нецелесообразно.
   Альтернатива — новая capability `systemd-integration`: отклонено, так как
   это приведёт к дроблению требований об одном пакете по двум спекам.

2. **MODIFIED для «Состав пакета» + ADDED для новых требований.**
   Требование «Состав пакета» формулировало старое поведение («только
   `/usr/bin/h1`») и обязано быть переписано целиком (полный блок из главного
   spec с новым содержимым). Новые требования (механизм юнитов, `h1.service`,
   conffile, `daemon-reload`) добавляются как ADDED — их раньше не было.
   Альтернатива — один большой MODIFIED-блок: отклонено, одно требование
   должно описывать одно поведение.

3. **Требования формулируются по наблюдаемому поведению пакета** (состав
   через `dpkg -c`, состояние через `systemctl`, журнал через
   `journalctl -u h1`, conffile-семантика через поведение dpkg при
   обновлении), а не по внутренностям CMake — по правилу проекта для спек.
   Имена опций CMake (`H1_INSTALL_SYSTEMD_UNITS`) упоминаются как
   пользовательский интерфейс сборки, а не как реализация.

4. **Проверка change — без C++-тестов.** GoogleTest-тесты бинарника не могут
   проверить состав deb-пакета; приёмка выполняется ручными smoke-кейсами
   (`dpkg -c`, установка/обновление/удаление пакета, `systemctl start`,
   conffile-сценарий). Задачи `ctest/valgrind` из правила проекта включены
   как регрессионная проверка того, что пакетные правки не сломали сборку
   приложения.

## Risks / Trade-offs

- [Правки `/etc/h1/h1.env` со старой (pre-conffile) версии пакета] → при
  первом обновлении до версии с conffile dpkg воспримет уже существующий
  локальный файл как изменённый conffile и спросит пользователя; в кейсах
  фиксируется ожидание и корректный ответ.
- [`cpack` выполняет install-правила всех подпроектов] → тестовые цели
  GoogleTest исключены из установки существующим `INSTALL_GTEST=OFF`; новые
  install-правила файлов этому не мешают. Регрессия ловится `ctest`.
- [Хардкод `/etc/h1` при локальном `cmake --install`] → install-правило
  пишет в реальный `/etc`; для рабочего процесса проекта (`make package`,
  CPack) это норма, переменная `H1_SYSCONF_DIR` позволяет переназначить.
- [Юнит включён в автозагрузку] → расчёт выполняется при каждой загрузке
  машины; это осознанное решение владельца (apply-фаза), отключается
  `systemctl disable h1`; поведение задокументировано в спеке и README.
- [`systemctl enable` при отсутствии systemd (например, сборка пакета в
  docker/chroot)] → все вызовы systemctl обёрнуты в
  `command -v systemctl` и `|| true`, скрипты никогда не роняют установку.

## Migration Plan

Реализация уже присутствует в репозитории; change фиксирует её статус:

1. Сверка артефактов change с фактическим состоянием репозитория
   (файлы `packaging/`, install-правила, README).
2. Регрессионная проверка сборки приложения (`ctest`, при необходимости
   clang-format/clang-tidy — правки затрагивают только CMake/конфиги).
3. Пересборка deb-пакета и прогон ручных smoke-кейсов из `manual-tests.md`.
4. Откат: правки локализованы в `packaging/`, `CMakeLists.txt`, `README.md`
   и файлах change — откат через git-историю этих файлов.
