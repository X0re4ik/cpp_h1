# http-api Specification

## Purpose
HTTP-сервер калькулятора `h1`: единственная ручка `POST /h1/task` принимает
операцию в JSON и возвращает результат расчёта в JSON, используя тот же
калькулятор, кеш и PostgreSQL, что и CLI-приложение.

## Requirements

### Requirement: Ручка расчёта POST /h1/task
Сервер SHALL предоставлять ровно одну прикладную ручку — `POST /h1/task`.
Тело запроса SHALL быть JSON-объектом того же формата, что принимает
CLI-приложение: для бинарных операций `{"left": <int>, "right": <int>,
"operation": "<+|-|*|/|^>"}`, для факториала `{"value": <int>,
"operation": "!"}`. Другие HTTP-методы на этом пути и другие пути SHALL
обслуживаться как ошибка маршрутизации.

#### Scenario: Успешный расчёт бинарной операции
- **WHEN** клиент отправляет `POST /h1/task` с телом
  `{"left": 2, "right": 3, "operation": "+"}`
- **THEN** сервер отвечает HTTP 200 с `Content-Type: application/json`

#### Scenario: Успешный расчёт факториала
- **WHEN** клиент отправляет `POST /h1/task` с телом
  `{"value": 5, "operation": "!"}`
- **THEN** сервер отвечает HTTP 200 и JSON-объектом с результатом `120`

#### Scenario: Неизвестный путь
- **WHEN** клиент отправляет запрос на путь, отличный от `/h1/task`
- **THEN** сервер отвечает HTTP 404 и не выполняет расчёт

#### Scenario: Неподдерживаемый метод
- **WHEN** клиент отправляет `GET /h1/task`
- **THEN** сервер отвечает HTTP 405 и не выполняет расчёт

### Requirement: JSON-контракт успешного ответа
Успешный ответ SHALL содержать HTTP-статус 200, заголовок
`Content-Type: application/json` и JSON-объект. Для бинарной операции объект
SHALL содержать поля `operation`, `left`, `right`, `result`, `fromCache`;
для факториала — `operation`, `value`, `result`, `fromCache`. Поле `result`
SHALL быть числом, `fromCache` — булевым значением, показывающим, взят ли
результат из кеша.

#### Scenario: Тело успешного ответа для сложения
- **WHEN** сервер успешно вычисляет `{"left": 2, "right": 3, "operation": "+"}`
- **THEN** тело ответа содержит `"operation":"+"`, `"left":2`, `"right":3`,
  `"result":5` и `"fromCache":false`

#### Scenario: Тело успешного ответа для факториала
- **WHEN** сервер успешно вычисляет `{"value": 5, "operation": "!"}`
- **THEN** тело ответа содержит `"operation":"!"`, `"value":5`,
  `"result":120` и `"fromCache":false`

### Requirement: JSON-контракт ошибки
Любая ошибка обработки ручки `POST /h1/task` SHALL возвращать HTTP-статус 500,
заголовок `Content-Type: application/json` и JSON-объект с непустым строковым
полем `error`. К ошибкам относятся невалидный JSON, неизвестная операция,
ошибка вычисления (например, деление на ноль) и внутренняя ошибка сервера.
Ручка `POST /h1/task` SHALL NOT возвращать иные HTTP-статусы, кроме 200 и 500.

#### Scenario: Невалидный JSON
- **WHEN** клиент отправляет `POST /h1/task` с телом `not-json`
- **THEN** сервер отвечает HTTP 500 и JSON-объектом с непустым полем `error`

#### Scenario: Ошибка вычисления
- **WHEN** клиент отправляет `{"left": 10, "right": 0, "operation": "/"}`
- **THEN** сервер отвечает HTTP 500 и JSON-объектом с непустым полем `error`

#### Scenario: Неизвестная операция
- **WHEN** клиент отправляет `{"left": 2, "right": 3, "operation": "%"}`
- **THEN** сервер отвечает HTTP 500 и JSON-объектом с непустым полем `error`

### Requirement: Использование кеша и PostgreSQL
Ручка `POST /h1/task` SHALL использовать общий с CLI механизм расчёта:
при наличии операции в кеше результат SHALL возвращаться без повторного
вычисления и без новой записи в БД (`fromCache: true`); при отсутствии —
SHALL выполняться расчёт, результат SHALL записываться в PostgreSQL и в кеш
(`fromCache: false`). Ошибочные операции SHALL также кешироваться и
сохраняться в БД в соответствии с существующим поведением CLI.

#### Scenario: Повторный запрос попадает в кеш
- **WHEN** клиент дважды отправляет одну и ту же операцию
- **THEN** первый ответ содержит `"fromCache":false`, второй — `"fromCache":true`,
  а в БД появляется только одна новая запись

#### Scenario: Успешный расчёт сохраняется в БД
- **WHEN** клиент отправляет ранее не встречавшуюся успешную операцию
- **THEN** в таблице `h1.calculation` появляется запись с операндами,
  операцией и результатом

### Requirement: Одновременная обработка запросов
Сервер SHALL обрабатывать несколько одновременных запросов без взаимных
блокировок, гонок данных и падений. Доступ к PostgreSQL и к кешу SHALL быть
сериализован; все одновременные запросы SHALL получать корректный ответ.

#### Scenario: Параллельные запросы завершаются
- **WHEN** к серверу одновременно отправлено несколько запросов расчёта
- **THEN** каждый запрос получает HTTP-ответ 200 или 500, сервер продолжает
  принимать новые запросы

#### Scenario: Нагрузочный прогон loadtest.py
- **WHEN** сервер запущен, а `python3 loadtest.py --requests 5000
  --concurrency 100` отправляет конкурентные запросы `POST /h1/task`
- **THEN** все запросы завершаются без ошибок соединения и таймаутов, сервер
  не падает и продолжает отвечать после прогона

### Requirement: Конфигурация серверного режима
Сервер SHALL принимать параметры запуска через CLI: `--host`, `--port`,
`--threads`, `--verbose` и `--help`. Значения SHALL переопределяться
переменными окружения `H1_SERVER_HOST`, `H1_SERVER_PORT`,
`H1_SERVER_THREADS`; приоритет — CLI, затем окружение, затем значения по
умолчанию (`0.0.0.0`, `8080`, `4`). `--help` SHALL работать без подключения
к PostgreSQL.

#### Scenario: Запуск с параметрами CLI
- **WHEN** сервер запускается с `--host 127.0.0.1 --port 9090`
- **THEN** он принимает соединения на `127.0.0.1:9090`

#### Scenario: Переопределение через окружение
- **WHEN** задана переменная `H1_SERVER_PORT=7070` и параметр `--port` не указан
- **THEN** сервер принимает соединения на порту 7070

#### Scenario: Справка без БД
- **WHEN** выполняется `h1Server --help` без переменных `DB_PG*`
- **THEN** команда выводит справку и завершается успешно

### Requirement: Прогрев кеша при старте сервера
Перед началом приёма запросов сервер SHALL загружать историю операций из
PostgreSQL в кеш тем же способом, что и CLI-приложение, чтобы повторные
операции из истории обслуживались как попадания в кеш.

#### Scenario: Операция из истории обслуживается из кеша
- **WHEN** сервер запущен на БД, где уже есть запись для операции, и клиент
  отправляет эту операцию
- **THEN** ответ содержит `"fromCache":true`

### Requirement: Серверный режим как отдельный бинарник
Серверный режим SHALL поставляться отдельным исполняемым файлом `h1Server`;
CLI-бинарник `h1` и его поведение SHALL оставаться без изменений.

#### Scenario: CLI не изменился
- **WHEN** после сборки выполняется
  `h1 --config '{"left": 2, "right": 3, "operation": "+"}'`
- **THEN** вывод остаётся `2+3=5.00`
